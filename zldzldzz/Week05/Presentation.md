## 1. 왜 스레드 풀을 사용하는가?

### 1.1. 문제 제기: 웹 서버와 같이 요청이 폭증하는 환경에서 매번 스레드를 직접 생성/소멸할 때 발생하는 비효율성.

- **주요 내용:** 서버에 요청이 들어올 때마다 새로운 스레드를 생성하여 처리하는 방식은 요청량이 많아지면 스레드의 **빈번한 생성과 소멸**로 인해 시스템에 큰 부하를 주고 성능을 저하시킵니다.

### 1.2 스레드의 기본 구조: OS 네이티브 스레드와 스레드 생성/소멸의 비용

- **주요 내용:** (Java 21부터 **Virtual Thread**(가상 스레드) 이전의 Java)Java의 스레드는 대부분 **OS 네이티브 스레드**에 직접 매핑됩니다. 따라서 스레드를 새로 생성하는 작업은 OS에 시스템 자원을 요청하는 **고비용 작업**이 됩니다.
    - 대부분의 경우에서 자바의 스레드는 OS 네이티브 스레드에 직접적으로 매핑됩니다. 따라서 스레드를 새롭게 생성하는 작업은 **시스템 리소스를 많이 소비**하게 됩니다.

## 2. 일반 스레드 사용 시의 한계와 오버헤드

### 2.1. 고비용 작업: 스레드 생성 및 종료 시 발생하는 시스템 리소스 소비(오버헤드).

- **주요 내용:** 스레드를 만들고 파괴하는 과정 자체에 CPU 시간과 메모리 자원이 소모됩니다.

### 2.2. 자원 비효율성: 통제되지 않은 스레드 수 증가로 인한 메모리 사용량 폭증 및 OOM(Out of Memory) 위험. (스레드당 스택 메모리 사용)

- **주요 내용:** 생성되는 스레드의 수에 제한이 없으면, 각 스레드가 사용하는 **스택 메모리** 때문에 전체 메모리 사용량이 급증하여 `OutOfMemoryError`가 발생하거나, 시스템이 불안정해질 수 있습니다.

### 2.3. 성능 저하: 과도한 스레드 생성/전환으로 발생하는 잦은 컨텍스트 스위칭 비용 증가.

- **주요 내용:** CPU 코어 수보다 훨씬 많은 스레드가 동시에 실행되려 할 때, OS는 작업을 번갈아 수행(Concurrency)하며 **컨텍스트 스위칭(Context Switching)**이 자주 발생합니다. 이 전환 과정(상태 저장/복원) 자체가 CPU 시간을 소모하는 오버헤드입니다.

## 3. 스레드 풀의 작동 원리와 장점

### 3.1. 스레드 풀의 개념: 미리 일정 개수의 스레드를 생성하여 재활용하는 방식 (풀링).

- **주요 내용:** 요청이 들어올 때마다 스레드를 생성하는 대신, 미리 정해진 크기의 스레드 그룹을 만들어 놓고 재사용하여 작업을 할당합니다.

### 3.2. 핵심 장점

- 자원 효율성/오버헤드 감소: 스레드 재사용으로 생성/종료 비용을 제거합니다.
- 안정성/제어: 스레드 개수 제한(`FixedThreadPool` 등)과 직업큐 통해 동시에 실행되는 스레드 수를 통제하여 시스템 부하를 조절합니다.
- 응답성 향상: 스레드 생성을 기다릴 필요 없이 즉시 작업을 할당할 수 있어 요청 처리 속도가 개선됩니다.

## 4. 블로그의 실험 기반 비교 분석

### 4.1 동일 조건(1000개 작업, 10ms 지연) 빠른 비교

| **비교 요소** | **일반 스레드 (1000개)** | **스레드 풀 (200개)** | **스레드 풀 (500개)** |
| --- | --- | --- | --- |
| **총 실행 시간** | 63 ms | 78 ms | **54 ms** |
| **초당 처리 작업 수 (RPS)** | 15,873 | 12,820 | **18,518** |
| **최대 활성 스레드 수** | 443개 | 202개 | 502개 |
| **스레드 생성 수** | 1,000개 | **200개** (재사용) | **500개** (재사용) |

### 주요 시사점 :

- **성능의 우위:** **스레드 풀 크기를 적절히 늘렸을 때(500개)**, 일반 스레드(63ms)나 풀 200개 설정(78ms)보다 훨씬 뛰어난 **가장 빠른 처리 속도(54ms)**를 보였습니다.
- **재사용의 이점:** 일반 스레드는 1,000개의 스레드를 모두 생성/종료하는 데 오버헤드가 발생하지만, 스레드 풀은 200개 또는 500개만 **생성 후 재사용**하여 자원 관리 효율을 높였습니다.
- **결론:** I/O 작업은 스레드가 대기하는 시간을 메우기 위해 **CPU 코어 수보다 많은 스레드**를 확보할 때 성능이 극대화됩니다. 스레드 풀을 통해 이 스레드 수를 효율적으로 관리하는 것이 중요합니다.

### 4.2. CPU 집중 작업 성능 분석: 물리적 코어의 한계

CPU 집중 작업은 복잡한 계산처럼 스레드가 CPU를 지속적으로 사용하며 **대기하지 않는(Non-Blocking) 작업**입니다. 이는 **물리적 CPU 코어 수**에 의해 실제 병렬 처리량이 제한됩니다.

| **비교 요소** | **일반 스레드 (1000개)** | **스레드 풀 (300개)** | **스레드 풀 (1000개)** | **스레드 풀 (2000개)** | **스레드 풀 (2000개)** |
| --- | --- | --- | --- | --- | --- |
| **총 실행 시간** | 449 ms | 418 ms | **193 ms** | 284ms | 351 ms |
| **초당 처리 작업 수 (RPS)** | 22,271 | 23,923 | 5,1813 | 35,211 | 28,490 |
| **최대 동시 활성 스레드 수** | 453개 | 302개 | 1002개 | 2002개 | 3002개 |

### 주요 시사점 (CPU 작업):

- **놀라운 결과:** 전통적으로 CPU 작업은 '코어 수'에 맞추는 것이 정답이었으나, 이 실험에서는 **스레드 풀의 크기를 1,000개로 늘렸을 때** **193ms**로 가장 빨랐습니다.
- **원인 분석:**
    - 이는 **I/O 작업이 아닌 순수 CPU 작업**에서도 **스레드 생성/소멸 오버헤드를 제거**하고 작업을 큐(Queue)에 넣어 일관성 있게 분배하는 **스레드 풀 자체의 관리 효율**이 성능에 크게 기여했음을 보여줍니다.
    - 또한, 일반 스레드 방식은 1,000개의 스레드를 생성했으나 동시 활성 스레드 수가 453개에 그친 반면, 스레드 풀은 **제한된 스레드를 재사용**하여 작업 처리량을 높였습니다.
- **결론:** 스레드 풀은 CPU 집중 작업에서도 스레드 생성 오버헤드를 제거하고 일정한 수의 스레드를 재사용/관리함으로써, **일반 스레드보다 우수한 성능과 안정성**을 제공할 수 있습니다.

### 4.3. I/O 작업 vs. CPU 작업 비교: 근본적인 차이

| **특성** | **I/O 집중 작업** | **CPU 집중 작업** |
| --- | --- | --- |
| **스레드 상태** | 대기(Blocking) 시간이 많음 | 지속적인 CPU 점유(Non-Blocking) |
| **최대 성능 전략** | **코어 수보다 많은 스레드**를 활용하여 대기 시간을 메꿔야 함. | **코어 수에 가까운 스레드**를 활용하여 컨텍스트 스위칭을 최소화해야 함. |
| **작업 시간 안정성** | 작업 시간이 상대적으로 **일정**함 (대기 시간이 주를 이룸). | 시스템 부하와 컨텍스트 스위칭으로 인해 작업 시간의 **변동 폭이 큼**. |
| **성능 (일반 스레드)** | 총 실행 시간이 매우 **짧음** (63ms). | 총 실행 시간이 상대적으로 **길게** 나타남 (449ms). |

**결론:** 작업의 특성(I/O vs. CPU)에 따라 시스템 자원을 활용하는 방식이 완전히 다르므로, **스레드 풀의 크기 설정은 작업의 성격에 맞게 튜닝되어야** 최고의 성능을 발휘할 수 있습니다.

## 6. 결론 및 요약

### 6.1. 최종 결론: 스레드 풀은 성능과 안정성의 균형점

- **스레드 풀(Thread Pool)**은 단순히 "더 빠르게" 만드는 도구가 아니라, 요청이 폭증하는 멀티스레드 환경에서 **스레드 생성/소멸 오버헤드를 제거**하고 **시스템 자원을 통제**하여 **안정적인 성능**을 유지하는 핵심 전략입니다.

### 6.2. 일반 스레드 vs. 스레드 풀 핵심 요약

| **구분** | **일반 스레드** | **스레드 풀** |
| --- | --- | --- |
| **리소스 관리** | 요청마다 스레드를 생성/파괴 → **고비용, 비효율적** | 미리 생성된 스레드를 재사용 → **저비용, 고효율적** |
| **시스템 안정성** | 스레드 수 통제 불가능 → **OOM, 컨텍스트 스위칭 급증 위험** | 스레드 수 제어 가능 → **안정적인 부하 관리** |
| **성능 튜닝** | 불가능 | 작업 특성에 따라 **최적의 풀 크기 튜닝**이 가능 (I/O vs. CPU) |
